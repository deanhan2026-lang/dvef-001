# 真实事故 → 判定单元（脱敏样例）

三个案例来自**我们自己的真实事故**，全部脱敏后按 DVEF-001 表达为判定单元，可被任何人复算。

| 文件 | 说明 |
|---|---|
| `cases_v1.json` | 3 条判定单元（含 digest、签名、`message_sha256`） |
| `../verify_cases.py` | 零依赖复算器：digest 三比对 → 规则重跑 → E-REASON 检查 → 验签 → 逐条反向测试 |

```bash
python3 verify_cases.py            # → 合计 3/3 通过（含逐条反向测试）
```

## 案例一览（判定本身是结论，事故背景是脱敏后的说明）

| # | 规则 | 结论 | 说的是什么 |
|---|---|---|---|
| 1 | `R-DENYLIST-MATCH` | `FAIL` / score 1 | **越权工具调用**：运行时工具集命中禁用清单（`shell.exec`） |
| 2 | `R-DRIFT-THRESHOLD` | `FAIL` / score 21 | **凭据暴露时长**：明文令牌表暴露 21 天，超出 7 天上限 |
| 3 | `R-SOURCE-AGREEMENT` | `INCONCLUSIVE` / `IN-SOURCE-CONFLICT` | **身份不绑定令牌**：客户端自报主体与令牌绑定主体不一致 |

第 3 条是这套格式最想说明的一件事：**当真源冲突时，正确结论不是"通过"也不是"不通过"，而是"判不了，并说明为什么判不了"**。
现实里的治理事故，多半发生在把这种情形硬写成任一二元结论的那一刻。

## 脱敏规则（我们遵守的）

- 不含任何凭据值、密钥、令牌、IP、内部路径、个人手机号与邮箱；
- 主体标识替换为占位符（`agent-redacted-A`）；轨迹号保留结构、替换内容；
- **判定所必需的数值原值保留**（暴露时长 21 天、工具清单、两个主体标识），否则案例就失去可复算性；
- 每个案例的 `case_meta.desensitization` 字段写明本案例具体去掉了什么。

## 关于签名

`cases_v1.json` 的签名使用**固定演示密钥**（`seed = SHA-256("DVEF-001-CASE-DEMO-KEY")`），
目的是证明"判定单元可签名、可验签、可交叉核对 `message_sha256`"。
**它不构成任何身份声明、不代表任何组织背书**，也不应被用于生产环境。

## 为什么要放真实事故

一份格式提案最容易被打回的地方是："你们自己遇到过吗？"
把真事故脱敏成可复算的判定单元，就不需要靠形容词回答这个问题——
**任何人可以跑 `verify_cases.py`，看到事故在格式里长什么样，以及它为什么必须判成这样。**
